# 任务包的设计原则

包的分类、流向和交接规则以插件的规则文件 `orgspec/rules.json` 为准，中文名在 `orgspec/terms.zh.json`。本文解释为什么这样分、每类包怎么写。

## 内容由接收方要做的事决定

| 任务包 | 方向 | 接收方要做的事 | 内容重点 | 不写 |
| --- | --- | --- | --- | --- |
| 需求包 | 本序列 +2 → +1（下发）；本序列 +1 → +0（执行）；本序列 +2 → 其他序列 +2（跨序列） | 规划并组织执行；照方法执行；决定接不接、怎么接 | 目标、逐条可检查的验收标准、资源和期限、会约束对方的决策、要交回的内容；方法只写给 +0，授权与边界只写给本序列的下一级 | 接收方职责内的事：给 +1 和其他序列不写具体方法，给其他序列不写对方内部怎么做；给 +0 不写和任务无关的背景 |
| 交付包 | 需求包的反方向 | 确认任务完成；决定下一步；；确认理解，或接收交付 | 结论先行、逐条验收对照、验收结论链接；+1 交回时加状态包、机制和边界、判断的变化、待决事项；；跨序列先在接单时逐条复述需求、承接范围和冲突，交付时写偏差；；做不到时写原因和建议 | 委托范围以外的判断；原始数据的罗列 |
| 送审包 | 任一序列 → 质量 +2 | 判断结论能不能信 | 结论原文、用途、证据编号、完整台账、已知弱点 | 推理过程和说服性文字 |
| 验收包 | 质量 +2 → 送审方 | 知道能说什么、要补什么 | 结论、可使用的结论原文、问题、失效条件、后续要求 | 对送审方方法的改写建议 |
| 决策包 | 任一序列 +2 → +3 | 拍板 | 背景、选项和代价、建议、截止时间 | 详细过程 |

同一个发出方写给不同对象，内容不同。以产品 +2 为例：

- 给产品 +1 的需求包，关系是下发：研究问题、需求文档框架、必须覆盖的判据、授权范围。+1 要据此组织调研和起草，所以要写清做到什么程度算完成、哪些事可以自己定。
- 给算法 +2 的需求包，关系是跨序列：需求文档里会约束规格的几条判据、成功阈值和停止条件。算法 +2 只需要知道这些约束，不需要产品序列内部的调研计划。
- 给研究员的决策包：待签的需求文档版本、选项和建议。

同一序列的上下两个方向也不同。产品 +2 给 +1 的需求包是一份约定：做什么、做到什么程度、哪些事能自己定。产品 +1 给 +2 的交付包是一份状态：结论是什么、判断变了什么、哪些事要 +2 决定。

## 需求包按关系决定发出方定多少

需求包的三种关系，差别只在一个维度上：发出方替接收方定了多少。职级越低，拿到的单子里已经填好的栏目越多：+0 拿到的需求包里连方法都写好了，+1 拿到的需求包里方法要自己定。

| 发出方定下的内容 | 下发（+2 → +1） | 执行（+1 → +0） | 跨序列（+2 → 其他序列 +2） |
| --- | --- | --- | --- |
| 目标、验收标准、资源和期限、继承的决策、交回要求 | 定 | 定 | 定 |
| 授权与边界 | 定：哪些事可以自己定、哪些要上报 | 定：哪些东西不能碰、超过什么阈值上报 | 不定，由对方自己定 |
| 本序列标准 | 定 | 定 | 不定，对方用自己的标准 |
| 方法 | 不定 | 定 | 不定 |
| 接单确认 | 默认不需要 | 不需要 | 需要 |

所以三种关系用一份模板，关系写在包头，由关系决定哪几栏要写、哪几栏只写“由接收方决定”。如果把关系做成包的类型，每多一种关系就要多出需求和交付两份模板，同一个栏目还会在几份模板里各叫一个名字，书记员没法按栏目同步字段。

交付包和需求包对称：委托时给了多少自主权，交回时就交代多少。执行关系只交对照结果和异常；下发关系还要交代结论为什么成立、判断变了什么、授权内做了哪些决定、哪些事要上一级决定；跨序列关系交付时写判断的变化、偏差和使用限制。

接单确认是需求包“交回要求”里的一个开关。跨序列一律要，因为对方序列可以拒绝，也可能按自己的标准理解需求；它不写成包，承接方 +2 把需求复述、承接范围和预计交付时间交回入口，由书记员填进跨序列需求的流转表单。下发默认不要，发出方判断目标容易被理解偏时改成要，+1 用一条带会话标签的评论确认。执行不要：方法已经写到命令，多一轮确认不划算。

送审包、验收包和决策包各自成类，因为它们的接收方要的内容和需求、交付相反。比如送审包故意去掉论证，免得质量序列被说服性文字带偏，交付包却要讲清机制和判断。

## 三层结构

任务包按记忆的三层结构写。

- 认知层：开头一段话。接收方先靠它判断这是什么、该交给哪个会话，再判断和自己当前目标的关系、要不要启动流程。各类包的认知层写法不同：下发关系的需求包写这个阶段要解决什么、为什么现在做；跨序列的需求包写请求和理由；交付包先写结论；送审包只写待审结论的原文；决策包写要研究员决定什么。
- 结构化层：按包的类型和关系固定的栏目。下发和跨序列关系的交付包里有一栏“判断的变化”，记下事情办完以后看法变了什么。
- 事实依据层：只放链接和编号，比如运行 ID、工作项、文档、数据和评测集版本。记录能组织、能检索的知识，不复制知识本身。

## 结构不变

同一类包、同一种关系，栏目固定。适用的栏目没有内容写“无”，不删；模板标“不写”的栏目整节删掉；不临时加栏目。同一个栏目在三种关系里用同一个名字。接收方每次都在同一位置找同一类信息，书记员也能按栏目把内容同步进飞书项目的字段。

## 只写当前状态

状态包依次写简介、当前状态、近期变化、风险。每次交接整体覆盖，只保留当前状态；近期变化越近写得越细，越远写得越粗。历史放进只追加的交接记录。接收方直接读状态包，不必回头翻历史。

简介写清这件事是什么，并点名涉及的会话、数据和产物版本，比如“算法 +1（会话 Alg-p1-02）”“规格 v2”“评测集 v1（14 天）”“节点 #142”。一条信息没带工作项 ID 时，路由靠工作项名称、字段和状态包判断它归哪个任务。书记员登记时，先用认知层那段话（送审包用待审结论）填上简介。

执行关系的交付包，状态包只写当前状态和风险两栏：+0 的上下文做完即释放，不需要近期变化。

## 通用包头

每份包的开头都是这几行；“关系”一行只有需求包和交付包有，“渠道”一行只有决策包有：

```markdown
- 包类型：
- 关系：下发 / 执行 / 跨序列
- 渠道：决策队列 / 研究员主动发起
- 发出方：序列、职级、会话名
- 接收方：序列、职级
- 关联工作项：
- 需要接收方做的事：规划并组织执行 / 照方法执行 / 决定是否承接 / 确认完成 / 决定下一步 / 接收交付 / 核查 / 拍板
- 回复期限：
- 上下文范围：只读本包和列出的链接（+0）／可以按事实依据继续检索（+1、+2）
```

## 做不到也是交付

如果验收只看做没做成，agent 会倾向于硬交一个结果。所以交付包有“做不到时”一栏，要写清尝试了什么、卡在哪里、缺的是哪类资源或条件、建议的解决办法。写清楚的“做不到”算合格的交付。
