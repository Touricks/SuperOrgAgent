# 任务包

一次交接写成一份任务包。包的内容由接收方要做的事决定：同一个产品 +2，写给本序列 +1 的需求包和写给算法 +2 的需求包，填的栏目和重点都不同。

`assets/` 放五类包的模板，用的时候复制一份再填，不改模板文件。`references/principles.md` 是设计依据，第一次用或拿不准某个栏目时先读；`references/interfaces.md` 是七个序列之间约定的接口；`references/examples.md` 是以一个代码优化器课题为例填好的包。

## 先判断包和关系

| 发出方 | 接收方 | 包 | 关系 | 怎么送到 | 模板 |
| --- | --- | --- | --- | --- | --- |
| 本序列 +2 | 本序列 +1 | 需求包 | 下发 | 派发 | `assets/request.md` |
| 本序列 +1 | 本序列 +0 | 需求包 | 执行 | 派发 | `assets/request.md` |
| 本序列 +2 | 其他序列 +2 | 需求包 | 跨序列 | 入口 | `assets/request.md` |
| 需求包的接收方 | 需求包的发出方 | 交付包 | 同所答复的需求包 | 交回；跨序列走入口 | `assets/delivery.md` |
| 非质量序列的任一级 | 质量 +2 | 送审包 | 无 | 入口 | `assets/review.md` |
| 质量 +2 | 送审方及其上一级 | 验收包 | 无 | 入口 | `assets/verdict.md` |
| 任一序列 +2 | 研究员 | 决策包 | 无 | 入口（决策队列，或研究员主动发起） | `assets/decision.md` |

需求包的三种关系，区别在发出方替接收方定了多少：执行关系连方法一起定好；下发关系定目标、验收标准和授权范围；跨序列关系只定要交付什么和本方的约束。交付包交代多少，和需求包给的自主权对应。

“怎么送到”一栏是本插件的机制：

- 派发：本序列上一级用 Agent 工具派下一级，提示里给出需求包草稿的路径。派 +0 之前，先请书记员把执行关系的需求包建成工作项并开工：登记请求里写来源工作项（所属阶段的下发需求包 ID），执行关系的需求包挂在它的主文档下。拿到工作项 ID 后，提示里单独写一行“会话名：<简写>-p0-<工作项 ID>”。
- 交回：子智能体结束时，最后一条消息只写包的路径和三行以内的摘要，正文都在文件里。
- 入口：写好草稿交回本序列 +2，由 +2 交给项目管理 +2（入口）。入口按路由结论转给对方序列的 +2、质量 +2 或研究员，书记员登记。+0、+1 不直接找别的序列。

## 交接规则

- 跨序列的任务包，接收方一律是对方序列的 +2。+0、+1 需要别的序列配合时，写进交给本序列上一级的交付包，由本序列 +2 发跨序列的需求包。
- 送审是唯一允许任何一级直接跨序列交接的情况：任何一级的执行结果都直接送质量 +2，由入口转交。
- 执行结果先送审，再交上一级。拿到验收包以后，交付包才交给需求包的发出方，结论用验收包里可使用的结论原文。质量序列自己的产出在序列内验收，不送审。
- 跨序列的需求包要接单确认：承接方 +2 把需求复述、承接范围和预计交付时间交回入口，书记员填进跨序列需求的流转表单，不另写交付包。和本方标准冲突时先流转到“协商中”；谈不拢的，写决策包交研究员。
- 约束某个序列的规则，不经由这个序列转交。比如“评测协议只读”约束的是工程，由算法 +2 直接发需求包给基础设施 +2。
- 项目管理分发的是信息，不写任务包。由信息引出的新任务，研究员决定后交给对应序列的 +2。
- 研究员在聚焦会话里当场定下的事，参与对话的 +2 写成决策包，渠道填“研究员主动发起”，交给入口。没写进台账的决定，对其他会话来说就不存在。
- 台账写入、信息分发、开工预检这类操作只记在工作项里，不写任务包，也不送审。
- 研究员和导师之间的材料由外联序列准备，不在本技能范围内。

## 再按序列填写

每份模板末尾有“各序列的填写要点”，写明七个序列在这类包里的具体内容；需求包和交付包按关系分开列。写跨序列的包时，另外查 `references/interfaces.md`，确认这两个序列之间约定交接什么。

## 草稿放在哪里

草稿写到 `packages/drafts/<序列>/YYYYMMDD-<包名>-<简称>.md`，序列用 product、alg、rnd、infra、quality、pmo、liaison。只写自己序列的目录。

标题和文件名按命名约定：包的标题写“<包名>：<任务名>”；书记员上传时改成“#<工作项 ID> <包名>（<作者会话名>）：<任务名>”，挂在下面的答复沿用同一个任务名。包头的“关联工作项”在登记前写“待建”，书记员登记后补上 ID。

## 写完自检

- 包头齐全：包类型、关系（只有需求包和交付包有）、发出方、接收方、关联工作项、需要接收方做的事、回复期限、上下文范围；决策包另有渠道。
- 认知层只有一段话，接收方读完就知道这是什么、要他做什么。
- 栏目和模板一致：适用于本关系的栏目一个不删，没有内容写“无”；模板标“不写”的栏目整节删掉；不临时加栏目。
- 没有越过接收方的职责：关系是下发或跨序列时，“方法”一栏只写“由接收方决定”；跨序列的需求包没有“授权与边界”；送审包不写推理过程和说服性文字。
- 交付包附了验收包的链接，结论用的是验收包里可使用的原文。
- 做不到时，写明缺的是哪类资源或条件，以及建议的解决办法。
- 事实依据只放链接和编号，不复制原文；认知层点名了涉及的会话、数据和产物版本，登记时它会成为状态包的简介。
- 决策包的“受影响的工作项”写全了；研究员主动发起的，“决定”一节当场写全。
- 用的是现行包名：需求包、交付包、送审包、验收包、决策包。

在部署过的项目目录里，`python3 -I .claude/agent-org/bin/orgspec.py lint <草稿路径>` 会检查包头、栏目和旧包名（项目权限只放行这种写法）。

## 存放（由书记员执行）

| 包 | 飞书项目 | 飞书文档 |
| --- | --- | --- |
| 需求包（下发、执行） | 新建同序列需求工作项，“关系”填下发或执行；“来源工作项”填上游工作项的 ID | 下发的放在同序列需求节点下的本序列节点；执行的放在来源工作项的主文档下 |
| 需求包（跨序列） | 新建跨序列需求工作项，归承接方序列 | 跨序列需求节点 |
| 交付包 | 不新建工作项；链接写进所答复工作项的“交付包”字段 | 挂在它答复的那份主文档下 |
| 送审包 | 新建送审工作项，“来源工作项”填被送审工作项的 ID | 送审节点下对应的序列节点 |
| 验收包 | 不新建工作项；写进送审工作项的结论字段，并写进被送审工作项的“验收结论”和“验收包” | 挂在它答复的送审包下 |
| 决策包 | 新建决策工作项；队列来的建成“待决定”，研究员主动发起的直接流转到“已决定” | 决策节点 |

作为主文档的包（需求包、送审包、决策包），上传时在模板栏目之后追加“状态包”和“交接记录”两节，简介先用认知层那段话（送审包用待审结论）填上：交接记录放在全文最后，用 append 追加；状态包整段用 block_replace 替换。命令、字段和 MQL 见 ledger 技能。
