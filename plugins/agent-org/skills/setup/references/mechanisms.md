# 组织设计怎样落到 Claude Code 上

## 生成的目录

```text
<项目目录>/
├─ CLAUDE.md                     所有会话都要知道的：研究任务、职级、交接规则、命名、东西在哪
├─ .claude/
│  ├─ settings.json              CLI 模式下主会话身份 pmo-p2；权限（allow/ask/deny）、hook 注册
│  ├─ agents/                    21 份定义：七个序列各三级；项目管理的 +1、+0 是 pmo-router、pmo-scribe
│  ├─ hooks/                     guard、instances、inbox、audit、pool 和它们读的 policy.json、lark-risk.json
│  ├─ agent-org/
│  │  ├─ bin/                    orgspec.py、ledger.py、route.py、pool.py、export_field_dictionary.py
│  │  ├─ orgspec/                规则文件和术语表的副本
│  │  ├─ templates/              五类包的模板副本
│  │  ├─ pool-plan.json          会话池模式：开池清单（会话名、开局句、各 +2 开的子会话）
│  │  └─ manifest.json           插件版本、运行模式、启用的序列、规则文件哈希、每个生成文件的哈希
│  ├─ state/                     instances.json（子智能体）；会话池模式另有 pool.json（认领表）和 sessions/（各会话的状态），都由 hook 维护
│  └─ logs/                      guard.jsonl（hook 的判断和提醒）；会话池模式另有 dispatch.jsonl（消息和认领）、compact/（压缩摘要）
├─ org/                          org.md（组织规则全文）、grants.md（授权表）、decisions.md、phases.md
├─ packages/drafts/<序列>/       任务包草稿；packages/sent/ 是书记员的登记回执
├─ inbox/                        各角色（会话池里是各会话）的收件箱、飞书私聊消息、开着的聚焦会话
├─ spec/                         实验规格、评测协议、需求文档（草稿，研究员签字后生效）和 task.json
├─ feishu/                       ids.json、字段字典、差异清单、写操作日志
└─ runs/                         运行记录
```

## 对照表

| 组织设计 | 在本插件里怎么做 | 依据和局限 |
| --- | --- | --- |
| 项目管理 +2 是研究员平时的入口 | CLI 模式：项目 settings 的 `agent` 设为 `pmo-p2`，在项目目录里运行 `claude` 就是入口。会话池模式：认领了 pmo-p2 的会话 `PMO-p2-01` | 入口长期运行，上下文会被压缩，所以它的定义要求每次从台账和状态包读状态。研究员特殊情况下直接委托其余六个 +2，谈定的事仍写成决策包交给入口 |
| +2 → +1 → +0 逐级派发 | 入口派各序列 +2；+2 派本序列 +1，+1 派本序列 +0；嵌套正好三层 | 嵌套子智能体默认最多三层，第三层没有 Agent 工具；层数由 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 控制。路由如果作为子智能体再去派 +2，+0 就派不出来了，所以路由只给结论 |
| 谁能派谁 | 派发图写在规则文件的 `dispatch` 一节，生成 policy.json 的 `spawn` 列表。这是规范：派了图外的角色，guard.py 只提醒、记日志 | 派发时带 `name` 仍然拒绝：开着 agent teams 时，带 name 的调用会变成队员，hook 认不出它的身份 |
| 跨序列只在 +2 之间，送审例外 | 序列内的 +1、+0 不能派别的序列；跨序列的包、送审包、决策包写成草稿逐级交回，由入口转交 | 送审包要经入口转交，交回链会在送审时回到入口；见下面“送审的往返” |
| 书记员是台账和文档唯一的写入方 | meegle 和 lark-cli 的写命令、`ledger.py` 的写子命令只放行 `pmo-scribe`（会话池里只放行唯一认领的书记员会话，子智能体和终端里的 `claude --agent pmo-scribe` 都不行）；其他会话只能加带标签的评论。`ledger.py --apply` 还加文件锁，同一时间只有一个写入 | 所有会话用的是研究员一个飞书账号，飞书的状态授权角色分不出是哪个会话，所以只能靠 hook 分权。hook 是防误操作的护栏，不是安全边界：它按命令文本判断，注释、换行、包装命令（`env`、`timeout`、`uv run` 等）、脚本文件、here-document、`find -exec`、`eval`、Python 的参数组合都认得，刻意混淆的命令藏得过去；真正的边界是研究员账号的权限 |
| 派 +1、+0 之前要有工作项 | +2、+1 直接请书记员登记自己的草稿，拿到工作项 ID 再派；登记请求写了“开工”的，书记员登记后接着流转到“执行中”，排队没派的留在“待开工” | 书记员除了项目管理 +1 的需求包，还接“登记请求”，请求方直接找书记员登记最快。已写进 `org/decisions.md` 开头的几处安排 |
| 会话名、会话标签 | CLI：instances.py 在子智能体启动时分配会话名，通过 additionalContext 告诉它；+0 的会话名由派发方在提示里写一行“会话名：Alg-p0-<工作项 ID>”，没写时 hook 提醒。会话池：会话名在开局句里，+0 的池位名是两位序号（Alg-p0-01），干活时仍用派活消息里那一行给的 Alg-p0-<工作项 ID> | hook 在 SubagentStart 时拿不到工作项 ID，所以 +0 要派发方给 |
| 并行上限 | CLI：instances.py 记在跑的实例，guard.py 在派发时检查上限：+2 一个、+1 三个、+0 五个，路由和书记员各一个。书记员到了上限拒绝，其余只提醒。会话池：上限是这个角色最多开几个会话，入口和书记员各只能有一条认领 | 12 小时没收到结束事件的子智能体按过期处理；会话池的会话不过期 |

## 会话池

任务文件写 `"mode": "pool"` 时，每个角色是一个研究员看得见的桌面会话。组织规则不变，变的是运行机制。

- **开池。** 研究员手工新建七个 +2 会话，各粘贴一句开局句；各 +2 照认领输出开出本序列的 +1、+0，入口开出路由和书记员，一共 21 个会话（任务文件的 `pool` 可以调）。侧栏里 +1、+0 挂在开它的 +2 下面。
- **认领。** 会话靠认领成为某个角色，认领要有许可：研究员的开局句（只认 +2），或者开它的会话用 `route.py expect` 做的预登记。hook 把许可转正成认领，`route.py` 自己从不写已转正的认领。认领表在 `.claude/state/pool.json`，guard.py 拦对它的编辑。认领后 hook 把角色定义（去掉开头的元数据）注入会话；压缩、恢复、清空上下文以后再注入一次，带上未了事项。
- **认身份。** hook 先看调用是不是子智能体（带 `agent_id`），再按会话 ID 找认领，再找许可。按桌面会话 ID 找到的认领，只有在原来的会话因为清空上下文而结束、新会话是清空以后开局的，才接到新会话上（恢复会话保留会话 ID，不用接）；从池会话里起的进程带着同一个桌面会话 ID，不算这个角色，没有写权。都没有的是研究员自己的会话：没有任何角色的写权；改评测协议的只读路径和 `.claude/`、high-risk-write 和带 `--yes` 的命令、派发带 `name`、不照规定写法的认领命令直接拒绝，写飞书和台账、在共享工作区切分支、释放认领弹窗询问。
- **派活。** 不用 Agent 工具派组织角色，给对方的会话发消息。先跑 `route.py pool --role <角色>` 找空闲的会话；没有空闲的就排队，研究员说“补位”时才开新会话。消息首行写抬头，比如 `【派活 #2101】Alg-p2-01 → Alg-p1-01：需求包 <路径>`。收方的 hook 把收到的时间记进 `.claude/logs/dispatch.jsonl`，这就是回执；它还按派发图、登记回执和负责会话核对消息，对不上的只提醒。
- **状态。** 每个会话的 hook 维护自己的状态文件：在忙、空闲、后台任务在跑、等研究员批准、失败、离线。`route.py pool` 汇总，`--watch` 每 30 秒刷新，`--recover` 在重启后列出要接着做的事。
- **硬规则。** 只管会损坏数据的事：书记员独写飞书（两条书记员认领时谁都不能写）、评测协议只读、high-risk 和带 `--yes` 的命令、在共享工作区里切分支、stash、reset 或 pull、`.claude/` 下的 hook、配置、角色定义和认领表不改、派发时不带 `name`、不用 Agent 工具派书记员、认领要有许可。hook 按命令实际执行的部分判断（`sh -c`、`eval`、包装命令都认得），Monitor 工具跑的命令和 Bash 一样检查。其余是规范，`route.py audit` 汇总提醒。
- **权限模式。** 全池用同一类：bypass 和其他模式之间，会话的消息会被扣下。hook 记下每个会话的模式，`route.py pool` 和 `setup.py check` 标出不同类的。bypass 和 dontAsk 下 hook 的询问一律换成拒绝，理由里写“请研究员在自己的终端运行”。

## 送审的往返

执行结果先送审，再交上一级。按嵌套的结构，送审是这样走的：

1. +0 做完，写交付包和送审包，交回 +1，摘要里写“待送审”。
2. +1 请书记员登记送审包：建送审工作项，把执行的同序列需求流转到“待验收”。+1 汇总后交回 +2，+2 交回入口。
3. 入口派质量 +2 核查；验收包出来后，书记员登记并流转。
4. 入口恢复这个序列的 +2（SendMessage 发给它上次的 agent ID），交验收包路径；+2 再恢复或重派 +1。

每次送审都要回到入口，链路长但规则清楚。如果实测太慢，有两个办法，都要研究员决定：调大嵌套层数，允许 +1 直接派质量 +2；或者把形式核查交给质量 +1 在序列内做，只有完整核查才回入口。

## 待实测的假设

| 编号 | 假设 | 不成立时 |
| --- | --- | --- |
| V1 | 主会话 → 序列 +2 → +1 → +0 三层派发能跑通，hook 认得每一层的身份 | 调大 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`；或者由入口直接派 +1、+0 |
| V2 | `claude --agent alg-p2` 开的聚焦会话里，hook 收到的 `agent_type` 是 alg-p2 | 聚焦会话改用单独的工作目录 |
