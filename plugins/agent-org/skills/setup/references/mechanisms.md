# 组织设计怎样落到 Claude Code 上

## 生成的目录

```text
<项目目录>/
├─ CLAUDE.md                     所有会话都要知道的：研究任务、职级、交接规则、命名、东西在哪
├─ .claude/
│  ├─ settings.json              主会话身份 pmo-p2、权限（allow/ask/deny）、hook 注册
│  ├─ agents/                    21 份定义：七个序列各三级；项目管理的 +1、+0 是 pmo-router、pmo-scribe
│  ├─ hooks/                     guard、instances、inbox、audit 和它们读的 policy.json、lark-risk.json
│  ├─ agent-org/
│  │  ├─ bin/                    orgspec.py、ledger.py、route.py、export_field_dictionary.py
│  │  ├─ orgspec/                规则文件和术语表的副本
│  │  ├─ templates/              五类包的模板副本
│  │  └─ manifest.json           插件版本、启用的序列、规则文件哈希、每个生成文件的哈希
│  └─ state/instances.json       在跑的实例、会话名和 agent ID（hook 维护）
├─ org/                          org.md（组织规则全文）、grants.md（授权表）、decisions.md、phases.md
├─ packages/drafts/<序列>/       任务包草稿；packages/sent/ 是书记员的登记回执
├─ inbox/                        各角色的收件箱、飞书私聊消息、开着的聚焦会话
├─ spec/                         实验规格、评测协议、需求文档（草稿，研究员签字后生效）和 task.json
├─ feishu/                       ids.json、字段字典、差异清单、写操作日志
└─ runs/                         运行记录
```

## 对照表

| 组织设计 | 在本插件里怎么做 | 依据和局限 |
| --- | --- | --- |
| 项目管理 +2 是研究员唯一的入口 | 项目 settings 的 `agent` 设为 `pmo-p2`，在项目目录里运行 `claude` 就是入口 | 入口长期运行，上下文会被压缩，所以它的定义要求每次从台账和状态包读状态 |
| +2 → +1 → +0 逐级派发 | 入口派各序列 +2；+2 派本序列 +1，+1 派本序列 +0；嵌套正好三层 | 嵌套子智能体默认最多三层，第三层没有 Agent 工具；层数由 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 控制。路由如果作为子智能体再去派 +2，+0 就派不出来了，所以路由只给结论 |
| 谁能派谁 | guard.py 按调用方的 `agent_type` 检查 Agent 调用，只放行 policy.json 的 `spawn` 列表 | 子智能体文件里 `Agent(类型)` 的限定会被忽略，只能靠 hook；派发时不能带 `name`，开着 agent teams 时带 name 的调用会变成队员 |
| 跨序列只在 +2 之间，送审例外 | 序列内的 +1、+0 不能派别的序列；跨序列的包、送审包、决策包写成草稿逐级交回，由入口转交 | 送审包要经入口转交，交回链会在送审时回到入口；见下面“送审的往返” |
| 书记员是台账和文档唯一的写入方 | meegle 和 lark-cli 的写命令、`ledger.py` 的写子命令只放行 `pmo-scribe`；其他会话只能加带标签的评论 | 所有会话用的是研究员一个飞书账号，飞书的状态授权角色分不出是哪个会话，所以只能靠 hook 分权。hook 是防误操作的护栏，不是安全边界：它按命令文本判断，注释、换行、包装命令（`env`、`timeout`、`uv run` 等）、脚本文件、here-document、`find -exec`、`eval`、Python 的参数组合都认得，刻意混淆的命令藏得过去；真正的边界是研究员账号的权限 |
| 派 +1、+0 之前要有工作项 | +2、+1 可以直接派书记员登记自己的草稿，拿到工作项 ID 再派；登记请求写了“开工”的，书记员登记后接着流转到“执行中”，排队没派的留在“待开工” | 书记员除了项目管理 +1 的需求包，还接“登记请求”，原因是 +1 在嵌套第二层，回不到路由。已写进 `org/decisions.md` 开头的几处安排 |
| 会话名、会话标签 | instances.py 在子智能体启动时分配会话名，通过 additionalContext 告诉它；+0 的会话名由派发方在提示里写一行“会话名：Alg-p0-<工作项 ID>” | hook 在 SubagentStart 时拿不到工作项 ID，所以 +0 要派发方给 |
| 并行上限 | instances.py 记在跑的实例，guard.py 在派发时检查上限：+2 一个、+1 三个、+0 五个，路由和书记员各一个 | 12 小时没收到结束事件的实例按过期处理 |
| 研究员按阶段和主责 +2 深谈 | 聚焦会话：入口登记后，研究员在同一目录运行 `claude --agent <角色>`；SessionStart 时登记为在跑实例，入口就派不出同一个 +2 | 依赖 SessionStart 的输入带 `agent_type`，待实测（V2、V3） |
| 入口转来的消息送到聚焦会话 | 入口用 `route.py notify` 写进 `inbox/<角色>.jsonl`；聚焦会话每次研究员发言时，inbox.py 把未读消息加进上下文 | 会话之间不能直接通信；研究员不发言就看不到（V4） |
| 研究员在飞书私聊里发消息 | `route.py listen` 订阅机器人收到的私聊，写进 `inbox/feishu.jsonl`，入口下一轮看到 | 要研究员本人在终端启动；收到私聊、写进 `inbox/feishu.jsonl` 在写入测试里实测过，入口下一轮读收件箱还没在真实会话里跑过（V4） |
| 没写进台账的决定不算数 | 聚焦会话谈定的事写成决策包（渠道：研究员主动发起），书记员登记后直接流转到“已决定” | 靠规则和入口的收尾步骤保证，hook 拦不住口头决定 |
| 评测协议只读、可改范围只给工程 | guard.py 按任务文件的路径拦写：`protected_paths` 除质量序列外一律拒绝，质量序列也要研究员确认；`editable_paths` 只给工程序列 | 只管 Claude 的文件工具；脚本在 shell 里写文件，要靠运行环境的只读挂载。放在项目目录以外的评测数据 hook 管不到，靠评测协议“存放和版本”一节的约定和账号权限 |
| 高风险命令 | settings 的 deny 拦 lark-cli 的 high-risk-write、带 `--yes` 的命令和登录、配置类命令；guard.py 再按风险表复核 | 风险表随 lark-cli 版本变化；本机版本和插件自带的静态表不同时，未知的写命令一律按写处理 |
| 身份 | 知识库、文档、云空间的命令要显式带 `--as user`，收发消息带 `--as bot` | |
| 写操作留痕 | 直接调用的写命令由 audit.py 记日志；`ledger.py` 自己记 | 都写进 `feishu/write-log.jsonl` |
| 插件自己的脚本 | guard.py 只信任 `.claude/agent-org/bin/` 下、内容和 manifest 哈希一致的脚本；改过的脚本里调用飞书命令行，一律按看不见的命令拦下 | |
| 跨阶段的记忆 | 各序列 +2 有项目级记忆（`.claude/agent-memory/<角色>/`） | 只记标准和判断；任务状态以台账为准 |

## 送审的往返

执行结果先送审，再交上一级。按嵌套的结构，送审是这样走的：

1. +0 做完，写交付包和送审包，交回 +1，摘要里写“待送审”。
2. +1 请书记员登记送审包：建送审工作项，把执行的同序列需求流转到“待验收”。+1 汇总后交回 +2，+2 交回入口。
3. 入口派质量 +2 核查；验收包出来后，书记员登记并流转。
4. 入口恢复这个序列的 +2（SendMessage 发给它上次的 agent ID），交验收包路径；+2 再恢复或重派 +1。

每次送审都要回到入口，链路长但规则清楚。如果实测太慢，有两个办法，都要研究员决定：调大嵌套层数，允许 +1 直接派质量 +2；或者把形式核查交给质量 +1 在序列内做，只有完整核查才回入口。

## 待实测的假设

| 编号 | 假设 | 不成立时 |
| --- | --- | --- |
| V1 | 主会话 → 序列 +2 → +1 → +0 三层派发能跑通，hook 认得每一层的身份 | 调大 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`；或者由入口直接派 +1、+0 |
| V2 | `claude --agent alg-p2` 开的聚焦会话里，hook 收到的 `agent_type` 是 alg-p2 | 聚焦会话改用单独的工作目录 |
| V3 | 聚焦会话开着时，入口派不出同一个 +2 | 靠入口登记兜底：`route.py focus open` 以后入口不派这个 +2 |
| V4 | 收件箱的消息在聚焦会话下一轮对话时能看到 | 在聚焦会话里手动运行 `route.py` 查收 |
| V5 | 用 SendMessage 能接着上次的 +2 干活 | 每次重派，靠状态包接续 |
| V6 | 插件装在用户级时，普通项目不受这些 hook 影响 | hook 只写在项目 settings 里，本来就只在初始化过的项目生效 |
| V9 | 只有书记员能写台账 | 加写入队列文件 |
