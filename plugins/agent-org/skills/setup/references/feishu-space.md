# 飞书空间：模板、复制和绑定

## 两层空间

meegle 命令行建不了工作项类型、字段和流转；开放接口能建字段、关系、角色和条件视图，改模板时只能改状态的名称、类型和授权角色，改不了流转线和表单，也建不了类型。所以空间结构由模板维护者提前配置，步骤见 `build-space.md`。新用户只复制和绑定；缺少模板应报告阻塞，不在初始化中现搭。

为了不让每个项目都从头搭一遍，空间分两层：

- 模板空间：每个实验室或企业搭一次，默认叫 std_template，任务文件的 `feishu.template_space` 可以改名。它只当复制源：只放结构，不放工作项，不跑项目。维护者自用视图不作为复制结果或初始化依赖。项目上的临时改动只改项目空间，不进模板，不然以后复制的项目都会带上。名字要和插件规则一字不差，用 `setup.py template --live` 核对到“可以当模板”为止，它也查模板里有没有工作项。
- 项目空间：每个项目一个，用模板的“分享空间配置”复制，名字写进任务文件的 `feishu.meegle_space`。同一企业内实测过：类型和字段的系统标识原样带过去，流程、流转表单和详情页布局也带过去；流程模板 ID 会变，自定义条件视图和空间置顶不带，系统预置视图可带入。插件初始化不创建或补齐自定义视图，禁止用 computer-use 配置视图。跨企业没有验证，不同版本之间（行业专版和其他版本、飞书项目和 Meegle）不互通。

模板改了以后，新复制的项目空间会带上；已经复制出去的不会跟着变，各自照绑定预览列出的清单补。

## 为什么要绑定

插件的规则文件只写设计，用中文名和英文标识描述，不带任何空间的 ID。type_key、field_key 和模板 ID 每个空间都不一样，复制出来的空间，模板 ID 也会变。每个项目在初始化时指定一个空间（任务文件的 `feishu.meegle_space`），再绑定一次：按名字或 `--map` 的指认，把规则里的类型和字段跟空间对上，把 type_key、api_name、模板 ID 和 field_key 记进项目的 `feishu/ids.json`。之后台账脚本只按这些键读写，空间里改名、插件改术语都不会断；键在空间里没了，下次绑定时报出来，重新指认。

## 步骤

1. 准备项目空间。任务文件写的空间还不存在的，照 `build-space.md` 从模板复制；企业里还没有模板的，报告缺少模板，由维护者另行准备。研究员要是空间管理员，配置类型、字段和流程要管理员权限。空间名写进 `init --task` 用的任务文件的 `feishu.meegle_space`，重跑 `init --apply`；有同名空间的，写 simple_name 或 project_key。
2. 预览绑定：`setup.py feishu --target <项目目录> --live`。它按任务文件里的空间名精确查出 project_key 和 simple_name，导出字段字典，把规则里的类型和字段跟空间对上，读回模板 ID、研究员的 open_id（`lark-cli whoami`）和知识空间的 space_id，刷新知识库节点的标题。全是读操作；可选的几项读不到只提醒，不中断。空间里一种插件类型都对不上时，只提示从模板复制，不打印整份清单。
3. 按打印出来的 `feishu/migration.md` 逐节处理：
   - “要处理的问题”：名字不同的用 `--map` 指认；缺的先在模板里补，再在本空间照样补。
   - “每种类型要有的东西”：照它建类型、状态和流转、流转表单的必填字段、角色、字段和选项，每个状态的授权角色都设成“研究员”。几种类型都有的字段（序列、发出方等），在一个类型上建好，再用“复制至其他工作项”加到别的类型上。
   - “知识库节点”：初始化时由执行 setup 的会话用 `ledger.py ensure-node all` 一次建齐，步骤见 setup 技能第四步“飞书文档”一节；以后单个补建由书记员用 `ledger.py ensure-node <键>`，都是先预览再 `--apply`。它只认上一级下标题完全相同的节点；知识空间里已经有、只是名字不同的，先在网页上改成清单里的名字，否则会另建一个。命令行没有给节点改名的子命令；节点标题跟着节点文档的一级标题走。先读一遍节点文档：空的，书记员用 `lark-cli docs +update --doc <节点链接> --command overwrite --doc-format markdown --content - --as user`，用 heredoc 传入一行 `# <新名>`；有内容的在网页上改，不要覆盖。
   - “读回”：还没有知识空间的，研究员确认后由 setup 技能运行，或者研究员自己运行 `lark-cli wiki +space-create --name "<知识空间名>" --description "<一句话>" --as user`。建完重跑第 2 步记下 space_id，再建节点骨架。
   - “模板维护说明”：详情页布局和项目详情页的标签页由维护者提前在模板里做好，复制时带入；缺项作为模板问题报告。
4. 改完重跑第 2 步，“要处理的问题”只剩已经知道、暂时不处理的项；加 `--apply` 写入。再重跑一次 `init --apply`，让 CLAUDE.md 和各角色拿到新的 ID。

以后空间有改动，从第 2 步重做。要改用另一个项目空间，照下一节做。任务文件写的空间和绑定的不一致时，台账脚本停下，等重新绑定。

## 换空间

已经绑定过的项目改用另一个项目空间，比如原来的空间建错了，或者要从模板重新复制一个。

- **空间按 key 认。** 加 `--live` 时，绑定脚本每次都按任务文件写的空间去飞书查一遍。查到的是上次绑定的空间，就照旧；查到另一个空间，就算换空间：原来的类型和字段绑定作废，按新空间重新绑定；查到几个同名空间，就停下来，列出各自的 simple_name。任务文件里的名字查不到、而它正是上次绑定的空间名的，按空间在飞书里改了名处理：接着用上次的 key，并提醒把任务文件改成新名字。
- **新空间先核对。** 新空间从模板复制，复制完先用 `setup.py template --space <新空间的 simple_name> --live` 只读核对。类型、字段、状态都对上、没有工作项，再往下做；缺东西就回模板补，再重新复制，不用 `--map` 绕过去。
- **任务文件不能有歧义。** 新旧空间同名时，`feishu.meegle_space` 写新空间的 simple_name 或 project_key，不写名字。改完重跑 `init --apply`。
- **预览里核对“换空间”一节。** `setup.py feishu --live` 会打印“换空间：旧空间 → 新空间”。`migration.md` 多出“换空间”一节，列出新旧空间的名字、simple_name 和 project_key，还有旧空间里有没有工作项。要看到“绑定：没有问题”，“要处理的问题”里也没有类型和字段的问题，才写入。
- **旧空间里有工作项就先停。** 插件搬不了工作项：meegle 只能建、查、改，不能把工作项移到别的空间。在新空间重建会换掉 ID，流转记录和评论也留在旧空间；本地的决策记录、`packages/sent/` 里的回执、包头的“关联工作项”和会话名里的工作项 ID，指的也都是旧空间。所以项目进行中尽量不换空间。真要换，旧空间留作档案，台账以后不再读写它；预览列出的没办完的工作项，由研究员逐条决定在新空间重建，还是在旧空间办完。研究员确认以后，写入时加 `--leave-old-items`。旧空间没查成的，也要加这个参数才写入。
- **写入时留下记录。** `feishu/ids.json` 的 `previous_spaces` 记下旧空间的 key、simple_name、名字、原来的绑定时间、换出的时间和还留在旧空间的工作项类型，本地记录里的旧 ID 以后还能查到属于哪个空间。写入后重跑一次 `init --apply`。
- **旧空间和知识库。** 旧空间留不留由研究员决定，删空间只能研究员本人做；模板空间不动。换项目空间不换知识库，知识库节点照旧。

## 视图复制实测与初始化边界

2026-11-03 在 std_template 的“同序列需求”下新建并保存公开“阻塞”条件视图，加入空间置顶后复制到独立测试空间。两边工作项类型标识一致；API 在模板中查到“阻塞”，在复制空间中返回空列表；复制空间能查到系统预置“全部”视图。自定义视图没有随配置复制。

据此，绑定和检查不再查询视图，迁移清单不列视图任务。Agent 使用 `queue`、`blocked`、`verifying`、`reviewing`、`open`、`recent` 台账查询，初始化不因缺少可视视图而失败。用户以后自行定制展示属于日常使用，不能加入插件的五分钟配置流程。

## 实测过的坑

- 状态授权角色是必填的，界面上不设保存不了；插件要求全部设成“研究员”。命令行建工作项时不传角色人员，工作项上的“研究员”角色就没有人，所以 `ledger.py register` 建工作项时带上 `role_owners`（研究员 = 当前账号）。
- 每个状态流都自带“已终止”：删不掉，`list-state-transitions` 不返回它，终止不算一次流转。视图默认不显示已终止的工作项，MQL 不会自动排除，`ledger.py` 的查询都显式排除它。
- 日期字段写目标日期的 UTC 中午。meegle 原样保存毫秒时间戳，网页按浏览者的时区显示，空间时区要升级版本才能改：按东八区零点写的日期，美东的人看是前一天；写 UTC 中午，UTC-12 到 UTC+11 的人看到的都是同一天。
- MQL 的表名只认 type_key 或类型的中文名，不认 api_name；结果在 `data.<分组>[].moql_field_list` 里，状态是 `key_label_value_list`。时间条件用 ``RELATIVE_DATETIME_BETWEEN(`updated_at`, 'past', '7d')`` 这类写法。
- `workitem get` 不返回人员字段的值：决定人填了，`--fields '["_all"]'` 和指定 field_key 读回来都是空的。MQL 能读到，类型是 `user_value`，带 name_cn、name_en、user_key 和 email；`ledger.py` 读人员字段改用 MQL，只取名字。
- `workitem` 命令的 `--work-item-type` 接受 api_name、type_key 和中文名；`view search` 的 `--view-scope` 只认 type_key，而且 `--key-word` 必填、按名字模糊匹配（查“决策”会同时返回“决策队列”和别的视图），要按 `view_name` 精确比对。
- 工作项的网页链接是 `https://project.feishu.cn/<simple_name>/<api_name>/detail/<工作项 ID>`；simple_name 和 project_key 不能互换。
- 一个空间里，关联类字段只能指向一种工作项类型，所以“来源工作项”用单行文本存 ID；查的时候用 `=`，“转成的工作项”存多个 ID，用 `LIKE`。
- lark-cli 只读当前目录、`/tmp`、`~/files` 下的 `@文件`；macOS 的临时目录不在其中。`ledger.py` 一律用 `--content -` 从标准输入传正文。
- `docs +create` 只返回 docx 链接和 document_id，没有知识库节点；要用 `wiki +node-get --node-token <document_id>` 换出 node_token，主文档字段存 `/wiki/` 链接。
- 所有 agent 用的是研究员一个账号，流转的授权角色分不出是哪个会话；谁能流转由 hook 管。
- 新建工作项的模板 ID 必填，每个空间都不一样，绑定时读回。
- `workitem meta-fields` 把多行文本报成 text，和单行文本一样；富文本才是 multi-text。所以绑定核对分不出单行和多行文本，建字段时在网页上看清类型。
- `workitem meta-types` 也列出空间里停用的系统类型（`is_disable` 为 1，比如需求、缺陷、版本、迭代），对它们查 `meta-fields` 会报找不到类型；导出字段字典时跳过它们。

## 没实测、先按推测处理的

- 自动化规则不通知操作者本人：没配过自动化，没测过。插件不依赖飞书通知，所以不影响运行；要用通知时先测一次。
- 研究员不是空间管理员时，当前负责人为空的工作项能不能流转。研究员是管理员时实测能流转；空间一般是研究员自己建的，就是管理员。
