# 实验规格和评测协议

两份文档都在项目的 `spec/` 下，初始化脚本按模板生成草稿：

| 文档 | 写什么 | 起草 | 签字 |
| --- | --- | --- | --- |
| `spec/spec.md` 实验规格 | 可改范围、目标指标、实验资源、搜索方法 | 算法 +2 | 研究员 |
| `spec/eval-protocol.md` 评测协议 | 数据、存放和版本、划分和可见性、接入方式、打分、重复和不确定性、证据标准 | 质量 +2 | 研究员 |

研究问题、目标和判据写在立项单里，这两份文档引用它，不重复。

## 怎么写

1. **先查，再问。** 动笔前把能查的查完：代码库的目录和入口、评测脚本、数据文件和规模、git 历史、已有的运行记录、需求文档。评测数据放在项目目录以外的，查清放在哪个系统、ID 和现在的版本。每节要弄清什么、先去哪里查，见 `references/questions.md`。
2. **写草稿。** 按模板的小标题写，每条句末标来源：
   - 〔研究员确认〕：研究员说过或确认过的。
   - 〔查到：<文件路径或命令>〕：从代码、数据或存放数据的系统里查到的，写明在哪里查到。
   - 〔推测，待确认〕：查不到、也还没问的。没把握的不要写成确定的样子。初始化时从旧版任务文件填进来的句子也标成这样，同样要问清。
3. **只问查不到的。** 把标〔推测，待确认〕的条目整理成问题，一次问三五个，附上你的推测和理由，请研究员确认或改正。不发长问卷，不问代码里查得到的事。
4. **请研究员签字。** 改到没有〔推测，待确认〕，写决策包请研究员签字，附文档链接和版本号；在聚焦会话里定下的，渠道写“研究员主动发起”。在“待签版本”里写明签字后要更新的字段：实验规格的版本写进“项目”工作项的规格版本（`spec_version`）；评测协议换了评测集的，新的评测集版本写进评测集版本（`evalset_version`）。决策流转到“已决定”以后，入口请书记员用 `ledger.py update <项目 ID> --set spec_version=<版本>` 这类命令写进去；决策队列里的决策要等研究员拍板，不在登记时写。
5. **改动照同样的步骤。** 评测协议在优化过程中保持不变，要改由质量序列提出、研究员签字。

## 任务文件里的几项

hook 和 CLAUDE.md 用的是任务文件里的这两项，要和文档一致：

- `editable_paths`：可改范围的可写路径，只有工程序列能写。
- `protected_paths`：评测协议用到的只读路径，比如评测脚本和评测集。

放在项目目录以外的评测数据不写进任务文件：在评测协议的“存放和版本”里写明在哪个系统、ID 和固定的版本号。hook 管不到这些数据，靠评测协议、CLAUDE.md 里的约定和账号权限。

要改的几项列进请求签字的决策包。研究员同意后，在普通会话里用 `agent-org:setup` 改任务文件、重跑 `init --apply`，hook 和 CLAUDE.md 才会跟上。agent 不直接改 `spec/task.json`。

## 谁来写、在哪里写

- 立项时（`agent-org:charter`），入口只收集研究问题、目标和判据，以及研究员已经知道的代码和数据位置。
- 设计阶段，研究员分别和算法 +2、质量 +2 开聚焦会话（`claude --agent alg-p2`、`claude --agent quality-p2`），各自用本技能访谈、起草。
- 不在聚焦会话里时不能直接问研究员：把问题写进决策包，交回入口。

## 拿不准时

- 研究问题还没定：先回立项单，不在规格里替研究员定方向。
- 项目没有启用算法序列：hook 不让任何角色改 `spec/spec.md`，实验规格由研究员本人写，问题单照样可以用。
- 评测数据只放在项目目录以外：正本最好在项目里也存一份，记下版本和校验和；外面的 ID 和版本号写进评测协议的“存放和版本”。
- 存放数据的系统分不出 dev 和 test：分成两份数据，或者用条目标签区分，划分规则写进评测协议的“划分和可见性”。
