# 立项

立项回答三件事：为什么做、做成了算什么、先做哪些。立项单是“项目”工作项的主文档，由研究员签字；阶段计划写进 `org/phases.md`，入口据此提醒研究员找哪个 +2 深谈，路由据此判断归属。

## 先问清，再写

一次问一个问题，研究员答不上来的写“待定”，不替他编。

1. 背景和范围：为什么要做，解决谁的什么问题，MVP 包含哪些、明确不做哪些。
2. 目标按 SMART 写：
   - 具体：要实现什么结果。
   - 可衡量：凭什么判断完成了，写成数字或可检查的条件。事前写下，事后定的标准容易向结果靠拢。
   - 可达成：以现有的时间、预算、算力和权限，怎么做到。
   - 相关：做成它，对研究员真正在意的方向有什么帮助。
   - 有时限：截止时间；周期长的设阶段里程碑。
3. 资源和成本：总预算、每个阶段的估算、超预算时找谁。
4. 停止条件：到什么程度就不再追加投入。

## RACI：角色 × 任务

按 `assets/charter.md` 里的表填，行是任务，列是研究员、导师和七个序列。四条检查规则写在模板里，填完逐条过：

- 一项任务有且只有一个 A。
- 一个角色 A 太多，说明负担过重。
- 一个角色既没有 R 也没有 A，要么给它责任，要么这个项目不启用它（初始化时用 `--sequences` 去掉）。
- 一项任务的 R 超过三个，要再拆。

## 先结果分解，再阶段分解

- 结果分解回答“要交付什么”：列出做完时必须有的成果，比如需求文档、规格、评测协议、实验流程、阶段结论、汇报材料，每项写验收条件。只做结果分解，容易漏掉依赖和顺序。
- 阶段分解回答“事情怎么推进”：按依赖把成果排进阶段，每个阶段写做什么、怎样算完成。只做阶段分解，容易只剩流程名称。
- 实验规格和评测协议在设计阶段写：算法 +2、质量 +2 用 `agent-org:spec` 访谈研究员后起草。立项时只记下研究员已经知道的代码、数据和评测脚本在哪里。
- 每个阶段加一栏主责序列。插件默认的对应是：搭设施找基础设施，设计找产品和算法，执行找工程，汇报前找外联；研究员可以改。

阶段计划按 `assets/phase-plan.md` 写，定稿后整张表写进 `org/phases.md`，“当前阶段”一行同步改。

## 落成第一批需求包

阶段计划签字后，第一阶段的主责序列 +2 收到第一份需求包。入口用 `agent-org:packages` 技能写下发关系的需求包：目标取自阶段的“做什么”，验收标准取自“怎样算完成”，资源上限取自阶段估算，继承的决策写“立项单 v1 已签字”。派书记员登记时写“开工：是”，书记员登记后接着流转到“执行中”，再把工作项 ID 交给这个 +2。

## 交给书记员

立项单写成草稿 `packages/drafts/pmo/YYYYMMDD-立项单-<项目名>.md`。研究员签字后，派 `pmo-scribe`：

```text
登记请求
- 动作：建“项目”工作项，主文档用立项单
- 草稿：packages/drafts/pmo/<文件>.md
- 字段：用 --set 传，标识见 org/org.md 的“字段”表（项目的阶段、总预算、已用预算、知识库空间等）
- 然后：需求文档、规格的链接留空，等产品和算法序列交付后补
```

书记员用 `ledger.py register <立项单草稿> --set <字段标识>=<值>` 建项目。`feishu/ids.json` 里已经有项目的（比如从旧空间导入的），加 `--existing`：把立项单挂到那个项目上当主文档，`--set` 的字段一并写进去，不再建新项目。立项单改过、要换主文档的，把修订版另存成新的草稿文件，再用 `--existing` 登记；登记过的文件不能再登记。项目 ID 自动写进 `feishu/ids.json`，以后建的工作项都带上“所属项目”。“项目”工作项由书记员按签字的立项单代建，负责人角色填研究员本人，研究员在网页上核对。项目从“立项中”流转到“进行中”时，流转表单要填知识库空间。

## 改阶段或主责序列

改阶段计划属于改目标或改范围，要研究员拍板：入口写决策包（渠道：研究员主动发起），书记员登记成“已决定”后，再改 `org/phases.md`，并通知受影响的序列 +2。
