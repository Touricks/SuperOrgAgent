# 台账结构

> 由 `scripts/orgspec.py` 从规则文件生成，测试会检查它和规则文件一致。改结构先改 `orgspec/rules.json`，再重新生成本文件。命令里一律用“标识”一列，中文名只给人看。

## 工作项类型

| 工作项类型 | 主文档 | 挂在下面的答复 | 由谁创建 |
| --- | --- | --- | --- |
| 项目 | 立项单 | 无 | 研究员 |
| 同序列需求 | 需求包 | 交付包 | 书记员 |
| 跨序列需求 | 需求包 | 交付包 | 书记员 |
| 送审 | 送审包 | 验收包 | 书记员 |
| 决策 | 决策包 | 无 | 书记员 |
| 反馈 | 导师原话所在的文档 | 无 | 书记员 |

## 状态和流转表单

| 工作项类型 | 状态 | 允许的流转 | 流转表单必填 |
| --- | --- | --- | --- |
| 项目 | 立项中、进行中、收尾、已结项 | 立项中→进行中；进行中→收尾；收尾→已结项 | 立项中→进行中：知识库空间 |
| 同序列需求 | 待开工、执行中、阻塞、待验收、已验收、归档 | 待开工→执行中；执行中→阻塞；阻塞→执行中；执行中→待验收；待验收→已验收；待验收→执行中；已验收→归档 | 执行中→阻塞：阻塞原因；执行中→待验收：送审包；待验收→已验收：验收结论、验收包；待验收→执行中：验收结论 |
| 跨序列需求 | 待接单、协商中、已接单、已拒绝、已交付、已关闭 | 待接单→已接单；待接单→协商中；协商中→已接单；协商中→已拒绝；已接单→已交付；已交付→已关闭 | 待接单→已接单：需求复述、承接范围、预计交付时间；待接单→协商中：承接范围；协商中→已接单：需求复述、承接范围、预计交付时间；协商中→已拒绝：承接范围；已接单→已交付：交付包 |
| 送审 | 待核查、核查中、已出结论 | 待核查→核查中；核查中→已出结论 | 核查中→已出结论：结论、可使用的结论原文、失效条件 |
| 决策 | 待决定、已决定、已过期、已执行 | 待决定→已决定；待决定→已过期；已决定→已执行；已过期→已执行 | 待决定→已决定：决定内容、决定人 |
| 反馈 | 待解析、待确认、已确认、已转任务 | 待解析→待确认；待确认→已确认；已确认→已转任务 | 待解析→待确认：类别；已确认→已转任务：转成的工作项 |

## 文档放在哪里

- 空间：每个项目建一个独立的知识空间。
- 一级节点：项目总览、同序列需求包、跨序列需求包、送审包、决策包、反馈包、汇报文档、归档文档。
- 按序列再分一层的节点：同序列需求包、送审包、归档文档。
- 下发关系的需求包放在同序列需求节点下的本序列节点。
- 执行关系的需求包放在来源工作项（所属阶段）的主文档。
- 交付包放在它答复的那份主文档。
- 跨序列关系的需求包放在跨序列需求节点。
- 送审包放在送审节点下对应的序列节点。
- 验收包放在它答复的送审包。
- 决策包放在决策节点。
- 反馈放在反馈节点。
- 上传和归位统一由书记员做。
- 阶段验收、归档时，把整棵子树移到归档节点下对应的序列；移动的是原节点，文档身份和链接都不变。
- 执行关系的需求包按验收标准划分，不按运行次数划分；每次运行靠运行 ID 记录。
