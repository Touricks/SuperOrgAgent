# 智能体组织插件使用说明

## 插件装好以后是什么样子

在一个项目目录里初始化以后，你平时只和一个会话说话：项目管理 +2，也就是入口；特殊情况下也可以直接找其余六个序列的 +2。你把信息和指示告诉入口，它按路由决策表把事情分给产品、算法、工程、基础设施、质量、外联六个序列的 +2，各序列再逐级派给 +1、+0。所有交接都写成五类任务包：需求包、交付包、送审包、验收包、决策包。书记员把它们登记进飞书项目、上传到飞书文档，你在飞书里打开视图就能看到每件事走到了哪一步。

你每天做两件事：看决策队列，替 agent 拍板它们超出授权的事；按阶段找主责序列的 +2 深谈，搭设施时找基础设施，设计时找产品和算法，执行时找工程，汇报前找外联。

插件有两种运行方式，在任务文件的 `mode` 里选。CLI 模式（默认）：在终端运行 `claude` 就是入口，其余角色是入口一级级派出的子智能体，你看不到它们在做什么。会话池模式：每个角色是桌面应用侧栏里的一个会话，七个序列的 +2 在顶层，各自下面挂本序列的 +1 和 +0；你能看到每个会话在做什么，也能点开任一会话直接交代，派活和交回都是会话之间的消息，留在各自的记录里。会话池模式见下面“会话池模式”一章。

插件只覆盖研究员和 agent 之间的协作。导师不用飞书，给导师的材料由外联序列准备，你确认后自己转交。

## 装之前准备好这些

| 要准备的 | 说明 |
| --- | --- |
| 飞书账号 | 能登录飞书项目和知识库，能在飞书项目里建空间；配置类型、字段要空间管理员权限 |
| lark-cli | 1.0.96 以上，已登录用户身份 |
| meegle | 1.0.23 以上，已登录；诊断上报建议关闭 |
| Claude Code | 2.1.219 以上，从这个版本起嵌套子智能体默认三层；会话池模式要用 Claude 桌面应用 |
| Python | 3.9 以上；插件的脚本只用标准库 |
| 飞书项目空间 | 实验室或企业里一个模板空间（默认叫 std_template，第一次初始化时搭），每个项目一个从模板复制出来的项目空间；你要是空间管理员。项目空间的名字写进任务文件，插件按它绑定 |

## 第一次：安装插件

插件装在用户级，装一次，所有项目都能用。

```bash
claude plugin marketplace add <本仓库的路径>
```

```bash
claude plugin install agent-org@agent-org
```

装好后，Claude Code 里多出六个技能：`agent-org:setup`、`agent-org:charter`、`agent-org:spec`、`agent-org:packages`、`agent-org:ledger`、`agent-org:entry`。插件本身不带任何会改变 Claude 行为的 hook：hook 只在初始化过的项目里、写在项目设置里，普通项目不受影响。

## 每个项目一次：初始化

在一个普通的 Claude Code 会话里说“用 agent-org 初始化这个项目”，它会调用 `agent-org:setup`，带你走下面几步。你也可以自己跑命令，`$PLUGIN` 是插件的安装目录（`claude plugin details agent-org` 能看到）。

**预检。** 查飞书客户端、两个命令行工具的版本和登录、飞书项目权限、诊断上报、飞书私聊的事件订阅、Claude Code 和 Python。失败项里要登录、升级、改设置的，都由你本人在终端执行。

```bash
python3 -I "$PLUGIN/scripts/setup.py" precheck
```

**写任务文件。** `agent-org:setup` 会先看代码库，再和你一起写。任务文件只放脚本和 hook 要用的几项：项目名和一句话简介、可改范围的可写路径（`editable_paths`）、评测协议用到的只读路径（`protected_paths`）、飞书项目空间名、模板空间名和知识空间名（`feishu`）、各角色用的模型、运行方式（`mode`，`cli` 或 `pool`）和会话池的大小（`pool`），格式见 `$PLUGIN/scaffold/task.example.json`。飞书项目空间必填，可以写空间名、simple_name 或 project_key；不写，初始化会停下。模板空间不写就是 std_template。研究问题、目标和判据在立项时写进立项单；实验规格和评测协议在设计阶段由 agent 访谈你以后写，见下面的“写实验规格和评测协议”。旧版任务文件里的 x、f、g、h 和 search 照样认。

**初始化项目目录。** 先预览，再写入。

```bash
python3 -I "$PLUGIN/scripts/setup.py" init --target <项目目录> --task <task.json>
```

```bash
python3 -I "$PLUGIN/scripts/setup.py" init --target <项目目录> --task <task.json> --apply
```

它会生成 21 个角色的定义、项目权限和 hook、`CLAUDE.md`、`org/`（组织规则全文、授权表、补充决定、阶段计划）、`packages/`、`inbox/`、`spec/`，以及插件脚本和规则文件的副本。已有的文件：上次生成后没人改过的直接更新；你改过的，新版本写在旁边的 `.new`，由你对照合并；`org/decisions.md`、`org/phases.md` 和 `spec/` 下除 `task.json` 以外的文档归你维护，建好以后不再动；`spec/task.json` 跟着 `init --task` 给的任务文件走，要改空间名、模型这类设置，改任务文件再重跑 `init`。同样的输入重复运行，报告“已写入 0 处”。初始化完会提醒还没绑定飞书空间。

**准备飞书空间。** 模板维护者提前配置类型、字段、流程、表单、角色和详情页，默认模板名为 std_template，只放结构，不放工作项。每个项目通过“分享空间配置”复制自己的空间，再绑定真实 ID。新用户不承担模板搭建；模板缺结构时报告阻塞，由维护者另行修复。自定义视图和空间置顶不随复制带入，插件已移除视图初始化要求，禁止在初始化中用 computer-use 配置视图。空间复制步骤见 setup 技能的 `references/build-space.md`；复制前只读核对模板：

```bash
python3 -I "$PLUGIN/scripts/setup.py" template --target <项目目录> --live
```

它只读，核对模板里的类型、角色、状态、字段和选项是不是和插件规则一字不差，也查模板里有没有工作项，最后一行是“可以当模板”才算好。流转、流转表单和详情页脚本读不到，照手册在网页上核对。

**绑定飞书空间。** 插件只定义台账的设计：工作项类型、字段和选项、状态和流转、流转表单、角色和视图，不带任何空间的 ID。每个项目把这套设计绑定到任务文件里写的空间一次，把空间里的键记进项目；之后台账只按这些键读写，空间里改名也不会断。没绑定以前，台账脚本不读也不写飞书。先预览：

```bash
python3 -I "$PLUGIN/scripts/setup.py" feishu --target <项目目录> --live
```

它按空间名精确查出空间（同名空间不止一个时停下来，请你把 simple_name 或 project_key 写进任务文件，重跑 `init --apply`），导出字段字典，把插件规则里的类型和字段跟空间按名字对上，核对字段类型和选项；还从 `lark-cli whoami` 读你的 open_id，按知识空间名查 space_id。这一步只读飞书，结果打印成建空间与核对清单（`feishu/migration.md`）：

- 空间里已经有、只是名字不同的，不用改名，用 `--map` 指认一次，比如 `--map same_seq=<空间里的类型名>`、`--map same_seq.relation=<空间里的字段名>`。标识在清单里查得到。
- 缺的结构先在模板里补，再在项目空间照样补，因为复制出来的空间不会跟着模板变；自定义视图不属于初始化，禁止用 computer-use 配置视图。空间里一种插件类型都对不上时，脚本只提示从模板复制，不打印整份清单。
- 飞书文档这一边：还没有知识空间的，你确认后由 setup 技能运行清单里给的 `wiki +space-create` 命令，你自己运行也行。有了知识空间，setup 技能用 `ledger.py ensure-node all` 把节点骨架一次建齐，同样先预览，你确认后才写。`setup.py check` 会报飞书这一边还缺什么。

核对没问题了，加 `--apply` 写入（要指认的照样带上 `--map`）：

```bash
python3 -I "$PLUGIN/scripts/setup.py" feishu --target <项目目录> --live --apply
```

写入的是 `feishu/ids.json`（空间的 project_key、各类型的 type_key 和模板 ID、各字段的 field_key、你的 open_id）、两份字段字典和清单。还有没绑上的类型或字段也可以先写入，用到它们时台账会停下报错，绑上以后就能用。一种类型都没绑上时，写入只记下空间和你的 open_id，不算绑定，台账脚本照样不读写飞书。以后改了空间，或者任务文件换了空间，重跑这条命令；任务文件写的空间和绑定的不一致时，台账脚本会停下等你重新绑定。最后重跑一次 `init --apply`，让 `CLAUDE.md` 和各角色拿到新的 ID。

**检查。**

```bash
python3 -I "$PLUGIN/scripts/setup.py" check --target <项目目录>
```

```bash
python3 -I -B "$PLUGIN/tests/test_plugin.py"
```

最后打开 `org/decisions.md`，开头列着插件定下的几处安排，请逐条确认或推翻。选了会话池模式的，绑定和飞书文档都做完以后开池，见“会话池模式”一章；开池以前 `check` 会提醒“会话池还没开齐”。

## 日常使用

### 和入口说话

在项目目录里运行 `claude`，这个会话就是入口 pmo-p2。第一件事是立项：说“立项”，入口用 `agent-org:charter` 和你一起写立项单和阶段计划。之后你说的每句话、转来的每条消息，入口都先过路由决策表：

| 你说的 | 入口怎么办 |
| --- | --- |
| 带工作项 ID 或会话名的，比如“#2101 的访谈记录补上了” | 在那个工作项下留评论，恢复负责的会话 |
| 没带 ID 的补充信息，比如“导师想看和人工基线的对比” | 派路由对照进行中工作项的名称、字段和状态包找归属；只对上一项就转过去，对上多项或一项也没有，回来问你 |
| 新任务 | 先问你要不要做、交给哪个序列；你拍板后由那个序列的 +2 写需求包 |
| 要你拍板的事 | 建成“待决定”的决策，进决策队列 |

说话时带上工作项 ID 或会话名，路由就不用猜。

### 看决策队列

每天入口会把待决定的决策交给你一次，紧急程度为“插队”的随时交。每件附选项、代价、建议和默认处理。你在入口会话里拍板，书记员把决策流转到“已决定”，再通知受影响的会话。到期没人决定的，照默认处理办。日常使用时可自行配置“决策队列”展示；初始化不要求此视图。

### 直接找某个 +2

想和某个序列的 +2 深谈，或者有件事想直接交给它时：会话池模式下，在侧栏点开它的会话直接说，它会自己告诉入口。CLI 模式下，先告诉入口“我想和算法 +2 谈规格 v3”，入口登记以后，你在项目目录另开一个终端：

```bash
claude --agent alg-p2
```

你直接和算法 +2 讨论，它能读台账、给本序列的 +1 派活。入口这段时间照规范不给它派活，有新信息留在它的收件箱，你下一次发言时它就能看到。结束前让它把谈定的事写成决策包，交给入口；书记员登记成“已决定”。谈定的事没写进台账就不算数，因为别的会话看不到你们的对话。

### 写实验规格和评测协议

立项以后进入设计阶段，分别直接找算法 +2、质量 +2 谈。它们用 `agent-org:spec` 先查代码库、评测脚本和数据，写出两份草稿：

- **`spec/spec.md` 实验规格**：可改范围、目标指标、实验资源、搜索方法。
- **`spec/eval-protocol.md` 评测协议**：数据、存放和版本、划分和可见性、打分、证据标准。

它们只把查不到的几个问题拿来问你。每条都标了来源：〔研究员确认〕、〔查到：…〕、〔推测，待确认〕，签字前你只需要核对标〔推测，待确认〕的条目。可写路径和只读路径要改的，会列在请你签字的决策包里；你同意后，在普通会话里改任务文件、重跑 init。

### 在飞书里给入口发消息

飞书私聊机器人的消息可以进入口。需要你在终端里启动监听，开着就行：

```bash
python3 -I .claude/agent-org/bin/route.py listen
```

消息落进 `inbox/feishu.jsonl`，入口下一轮对话时看到。监听只收你本人发给机器人的私聊，按消息 ID 去重；`feishu/ids.json` 里没有你的 open_id 时，它不会启动，免得谁私聊机器人都能进入口。没开监听时，把消息转述给入口也一样。

### 在飞书里看进度

Agent 用 queue、blocked、verifying、reviewing、open、recent 查询台账，分别读取决策队列、阻塞、待验收、待核查、未完成和近 7 天变化；open 还排除了已验收。自定义视图不属于初始化和验收要求。飞书文档里每个项目一个知识空间，同序列需求包按序列分节点，再沿委托关系往下挂：阶段的下发需求包下面挂执行需求包，答复挂在它答复的那份包下面。

## 会话池模式

任务文件写 `"mode": "pool"`，每个角色就是桌面应用侧栏里的一个会话。组织规则和台账都不变，变的是会话怎么开、怎么找人、怎么交接。

**开池前。** init、飞书绑定和知识库节点都做完；插件的插件市场来源不在项目目录里（否则池里的会话改得到插件本身）；想好你的全局 CLAUDE.md 里和会话池冲突的规则怎么办，比如“要回 ACK”“先核实授权链”“全自动流水线放在单个会话里”，这些只能你本人改。

**开池，大约二十分钟，你要在场。**

1. 运行 `python3 -I "$PLUGIN/scripts/setup.py" pool --target <项目目录>`，打印开池清单。
2. 在桌面应用里选中项目目录，在模式选择器里选会话池用的模式，模型先选 +2 用的那个。全池用同一类模式：bypass 和其他模式之间，会话的消息会被扣下，大约五分钟后丢掉。
3. 手工新建七个会话（New session，目录选本项目，不开 worktree），每个粘贴清单里的一句，比如“认领 alg-p2（会话名 Alg-p2-01），然后照认领输出开出本序列的 +1 和 +0”。hook 按这句话直接认领，它会开出本序列的 +1、+0，挂在自己下面；入口会开出路由和书记员。
4. 再跑一次 `setup.py pool`，看到认领数等于清单的会话数、入口和书记员各一条，就开好了。在入口会话的终端窗格里运行一次 `python3 -I .claude/agent-org/bin/route.py pool --watch`，然后对入口说“池开好了”。

**平时。** 找入口 `PMO-p2-01` 说话；想直接交代某个序列，点开它的会话说，它会标成“研究员在用”并告诉入口，这期间入口不给它派活。进度看 `route.py pool --watch`：等你批准的、失败的、像是卡住的排在最前；台账才是正本。

**会话之间怎么交接。** 派活、交回、登记请求、送审、需拍板都是消息，首行一个抬头，比如 `【派活 #2101】Alg-p2-01 → Alg-p1-01：需求包 <路径>`，正文在包文件里。派活前先用 `route.py pool --role <角色>` 找空闲的会话；没有就排队，活留在台账的“待开工”。收方的 hook 把收到的时间记进 `.claude/logs/dispatch.jsonl`，对不上派发图、没有登记回执的会提醒收方，但不拦。

**多开、恢复、换人。**

- 要多开会话：在那个序列 +2 的会话里说“补位”或“再开一个 alg-p0”。你不说，会话不会自己开，只记补位请求，进入口的每日决策队列。
- 重启或电脑睡眠以后：对入口说“恢复”，它照 `route.py pool --recover` 的清单逐个续上，书记员先补完写到一半的登记。
- 某个 +2 会话丢了：先运行 `route.py release <会话名>` 释放旧的认领，再新建一个顶层会话，粘贴重建句（`setup.py pool` 在这个 +2 下面列出，也在 `.claude/agent-org/pool-plan.json` 的 `rebuild` 里）。
- 不要让会话去归档、清空或停止别的池会话；归档一个 +2 会连带它下面已经空闲的子会话。要收掉，由你本人在侧栏操作。

**升级插件。** 重跑 `init --apply`，然后退出并重开桌面应用；各会话下一轮开始时，hook 注入新的角色说明。`setup.py check` 会列出还停在旧版规则上的会话。

**回到 CLI 模式。** 任务文件改回 `"mode": "cli"`，重跑 `init --apply`；池会话由你在侧栏归档，`.claude/state/` 和日志留着也无害。

## 一项任务怎样走完一轮

以“产品序列起草需求文档”为例：

| 步骤 | 谁 | 做什么 | 台账里的变化 |
| --- | --- | --- | --- |
| 下发 | 产品 +2 | 写下发关系的需求包，请书记员登记并开工，再派产品 +1 | 同序列需求“执行中”（排队还没派的留在“待开工”） |
| 拆分 | 产品 +1 | 按验收标准拆成执行关系的需求包，请书记员登记并开工（登记请求里写来源工作项，也就是所属阶段的下发需求包 ID），拿到工作项 ID 后派产品 +0（会话名带这个 ID） | 新的同序列需求“执行中”，主文档挂在下发需求包的主文档下 |
| 执行 | 产品 +0 | 访谈整理、现状调研；写交付包和送审包，交回 +1 | — |
| 送审 | +1 → +2 → 入口 → 质量 +2 | 书记员建送审，执行的工作项流转到“待验收”；入口派质量 +2 核查 | 送审“待核查”→“已出结论” |
| 验收 | 质量 +2 | 写验收包：接受、缩小或否决，附可使用的结论原文 | 执行的工作项“已验收”，或退回“执行中” |
| 交付 | 产品 +1 → +2 | 用验收包里的结论原文写交付包，交上一级 | 下发的工作项挂上交付包 |
| 决策 | 产品 +2 → 研究员 | 需求文档要签字，写决策包进队列 | 决策“待决定”→“已决定” |

每次送审都要回到入口转一次：CLI 模式下嵌套的子智能体最多三层，序列内的 +1 派不出质量 +2；会话池模式下送审包也一律发给入口，由入口登记后转给质量 +2。

## 六个技能各管什么

| 技能 | 管什么 | 谁用 |
| --- | --- | --- |
| `agent-org:setup` | 预检、初始化项目目录、搭模板空间、复制项目空间、绑定飞书空间、开会话池、检查漂移 | 你，在普通会话里 |
| `agent-org:charter` | 立项单、阶段计划和主责序列、第一份需求包 | 入口和你 |
| `agent-org:spec` | 访谈以后写实验规格和评测协议，每条标来源 | 算法 +2、质量 +2，你直接找它们时一起写 |
| `agent-org:packages` | 判断包和关系、五类包的模板和填写要点、写完自检 | 所有序列 |
| `agent-org:ledger` | 查台账；书记员登记、流转、改字段、归档 | 所有角色读，书记员写 |
| `agent-org:entry` | 路由决策表、决策队列、聚焦会话、飞书私聊 | 入口和路由 |

## 哪些事 agent 做不了，要你本人来

hook 会拦下这些操作，入口会把完整命令写给你：

- 登录、登出、升级命令行工具，改它们的配置和诊断上报设置。
- lark-cli 风险表里的 high-risk-write 命令，以及任何带 `--yes` 的命令。
- 签字：需求文档、规格、权限策略、质量和算法之间的争议、超预算、不可逆的对外动作、停止或转向、发给导师的材料。
- 删空间、删类型、删字段。模板维护者可另行配置类型、字段和流转表单。新用户初始化只复制、绑定，不搭模板，也不配置自定义视图。

hook 只拦会损坏数据的事：工作项、字段、状态和文档只有书记员能写（会话池里只有认领了书记员的那一个会话能写，不用 Agent 工具派书记员；CLI 模式下书记员同时只能有一个）；评测协议用到的文件（评测脚本、评测集）只读，只有质量序列能提出修改，还要你确认；`.claude/` 下的 hook、配置、角色定义和认领表谁都不改，要改就改插件或任务文件再重跑 init；派发时不能带 `name`；会话池的会话不在共享目录里切分支、stash、reset。改评测协议的只读路径和 `.claude/`、high-risk-write 和带 `--yes` 的命令、派发带 `name`、CLI 模式的第二个书记员、会话池里用 Agent 工具派书记员，在你自己的会话里也直接拒绝；书记员以外写飞书和台账、会话池里切分支和释放认领，在你自己的会话里弹窗问你。会话是 bypass 模式时，本该弹窗问你的一律直接拒绝，理由里写“请研究员在自己的终端运行”。

其余是规范，hook 只提醒、记日志，不拦：谁能给谁派活、派 +0 要写会话名、可改范围里的代码只由工程序列改、各序列写自己的草稿目录、书记员以外的并行上限。提醒记在 `.claude/logs/guard.jsonl`，会话池模式下 `route.py audit` 汇总。

路径边界只管 Claude 的文件工具（Edit、Write）：在 shell 里写文件（`echo > …`、`sed -i`、`cp`）拦不住，要靠运行环境的只读挂载。放在项目目录以外的评测数据 hook 管不到：在评测协议的“存放和版本”里写明放在哪、固定哪个版本，靠这条约定和账号权限保护。

hook 是防 agent 误操作的护栏，不是安全边界。它按命令文本判断：换行、注释、`cd`、包装命令（`env`、`timeout`、`uv run` 等）、脚本文件（用 bash、python 运行或直接运行）、here-document 和 here-string、管道、`find -exec`、`eval`、Python 的各种参数写法都认得，但刻意混淆的命令总有办法藏过去。所有 agent 用的是你一个飞书账号，真正的边界是这个账号的权限；hook 的判断都记在 `.claude/logs/guard.jsonl`，可以抽查。

## 插件定下的几处安排

插件按下面几条安排落地。初始化时它们会列在 `org/decisions.md` 开头，你可以逐条推翻：

- 项目管理 +2 是入口，每日决策队列由它交给你。
- 跨序列需求的接单确认填在流转表单里：待接单到已接单确认接单，协商中到已拒绝要填承接范围，已接单到已交付要附交付包。
- 同序列需求用“关系”字段区分下发和执行；决策有“渠道”字段，反馈也有“主文档”字段。
- 书记员除了接项目管理 +1 的需求包，也接各序列 +2、+1 的登记请求，只登记它们自己的草稿。原因是派 +1、+0 之前要先有工作项 ID，请求方直接找书记员登记最快。
- 各会话可以自己加带会话标签的评论；工作项、字段、状态和文档仍只由书记员写。
- “项目”工作项由书记员按你签字的立项单代建，负责人填你本人，你在网页上核对。
- 决策包包头多了“紧急程度”和“默认处理”两行，对应决策工作项已有的两个字段。
- 你可以直接委托其余六个序列的 +2，不必都经过入口；谈定的事仍写成决策包交给入口登记。
- 会话池模式下，派活、交回、登记都发消息；书记员的写权只认唯一的那条认领；派发时带 name、在共享目录里切分支或 stash 按硬规则拒绝，其余派发规则是规范加审计。

## 在飞书项目里做不到、改成别的办法的

| 想做的 | 飞书的限制 | 插件的办法 |
| --- | --- | --- |
| 用命令建工作项类型、字段、流程 | meegle 建不了，开放接口也建不全 | 在网页上搭一个模板空间（你点或会话代点），每个项目从模板复制；插件按名字绑定，名字不同的指认一次 |
| 用命令建条件视图、放进空间置顶 | meegle 建不了，复制空间也不带过去 | 从初始化和验收中移除；禁止在初始化中用 computer-use 配置视图，Agent 直接查询台账 |
| 一个字段关联多种工作项 | 关联字段在一个空间里只能指向一种类型 | “来源工作项”用单行文本存 ID |
| 按会话分流转权限 | 所有 agent 用你一个账号，授权角色分不出会话 | 由 hook 管谁能写、谁能流转 |
| 用飞书通知提醒 agent | 推测自动化不通知操作者本人，而操作者就是你的账号（没实测） | agent 不依赖通知，靠台账查询和收件箱 |
| 在详情页看到全部字段 | 默认只显示“名称” | 在模板各类型的详情页布局里把主文档、来源工作项等字段放出来，复制时一起带过去；清单的“网页上还要做的事”里列着 |
| 不设状态授权角色 | 授权角色是必填的；命令行建工作项不填角色人员时，角色上没有人 | 每个状态的授权角色都设成“研究员”；建工作项时把你填进“研究员”角色 |
| 读回人员字段 | `workitem get` 不返回人员字段的值，决定人填了读回来也是空的 | 台账脚本改用 MQL 读，只显示名字 |
| 让 MQL 和视图查同一批工作项 | 每个状态流自带“已终止”，视图默认不显示，MQL 不会自动排除 | 查询都显式排除“已终止”；终止不算流转，要你在网页上操作 |
| 在项目详情页用“视图”控件 | 要旗舰版 | 用“工作项视图”控件 |
| 用命令给知识库节点改名 | lark-cli 没有改节点标题的子命令 | 节点标题跟着节点文档的一级标题走；空文档整篇覆盖，有内容的在网页上改 |
| 让日期在谁看都是同一天 | 日期存成毫秒时间戳，网页按浏览者的时区显示；空间时区要升级版本才能改 | 日期字段一律写目标日期的 UTC 中午，UTC-12 到 UTC+11 的人看到的都是同一天 |

## 升级和检查

插件更新后，在项目里重跑 `init` 预览差异：没人改过的文件直接更新，改过的写 `.new`。`feishu/ids.json` 不是新版格式的，`setup.py feishu --live` 会提醒重新绑定，绑定以前台账脚本不读写飞书。`check` 按项目里的 `spec/task.json` 用现在的插件重新生成一遍，和初始化时逐个文件比对：插件脚本、模板、规则、术语表或 `feishu/ids.json` 变了，它列出受影响的文件，提醒你重跑 `init`；你改过的文件和没合并的 `.new` 也会列出来。手改过 `spec/task.json` 的，单独报一条，先不比对插件更新；本机 lark-cli 的版本让 init 要换风险表的，单独报一条；本机 lark-cli 只是比插件自带的表新，打一行提醒。`spec/` 下的文档归你维护，插件改了模板也不会覆盖；init 会提醒哪份还是旧模板，可以请算法 +2、质量 +2 用 `agent-org:spec` 按新模板重写。旧版任务文件（x、f、g、h、search）照样认，`spec/task.json` 会写成新格式。组织规则（职级、包、路由表、台账结构）只在插件的 `orgspec/rules.json` 里存一份，中文名在 `orgspec/terms.zh.json`。类型、字段、包和序列改名只改术语表：脚本和 hook 按英文标识走，飞书查询按绑定时记下的键走，空间里的名字不用跟着改；状态名和选项名直接写在 `rules.json` 里，台账查询也直接用到几个状态名（待决定、阻塞、待验收、待核查等），改状态名要同时改 `rules.json`、`ledger.py` 的查询和飞书空间。插件的台账结构改了，先在模板空间里补齐，用 `setup.py template --live` 核对到“可以当模板”；已经在用的项目空间不会跟着变，各自重跑绑定预览，照清单补。

## 常见问题

**入口说“派不出去，已有一个在跑”，或者“没有空闲的会话”。** 每个序列的 +2 只能有一个，+1 三个，+0 五个。CLI 模式下，要么有子智能体还没交回，要么你正和这个 +2 开着聚焦会话，`.claude/state/instances.json` 里能看到在跑的实例；只有书记员这一条会拦，其余到了上限只提醒。会话池模式下，活留在台账的“待开工”里排队，等有会话交回；要多开会话，你在那个序列 +2 的会话里说一句“补位”。

**台账脚本说“还没绑定飞书空间”，或者任务文件里的空间和绑定的不同。** 跑 `setup.py feishu --target <项目目录> --live` 看绑定结果，核对后加 `--apply`。

**绑定预览说空间里没有一种类型对得上。** 这是个空白空间。项目空间要从模板复制：先用 `setup.py template --live` 核对模板，再照搭建手册用模板的“分享空间配置”复制，把复制出的空间名写进任务文件。企业里还没有模板的，先搭模板。

**要把项目换到另一个飞书项目空间。** 照 setup 技能 `feishu-space.md` 的“换空间”一节做：新空间从模板复制，先用 `setup.py template --space <simple_name> --live` 核对；任务文件写新空间的 simple_name；`setup.py feishu --live` 的预览会多出“换空间”一节，列出旧空间里有没有工作项。插件搬不了工作项，旧空间里的工作项留在原处当档案，你确认以后才加 `--leave-old-items` 写入。项目进行中尽量别换空间。

**书记员说“字段还没绑定”。** 看 `feishu/migration.md` 的“要处理的问题”：空间里没有的，先在模板里补，再在本空间照样补；已经有、只是名字不同的，用 `--map` 指认。再跑 `setup.py feishu --live --apply`，字段的 field_key 记进 `feishu/ids.json`，书记员就能用了。

**书记员说“上次已经建了工作项，但没做完”。** 登记到一半失败了，比如建文档时断网。工作项已经在了，回执在 `packages/sent/<ID>.json`（同一个项目已经有别的立项单的回执时，是 `<ID>-<草稿文件名>.json`）。修好原因后让书记员加 `--resume` 接着做，它不会再建一个。

**书记员说“上次建文档没有拿到确定的结果”。** 建文档超时，或者返回里没有链接时，文档可能已经建好了。到提示里的节点下看一眼：建好了的，让书记员重跑时加 `--doc <文档链接>`；确认没建成的，加 `--doc new`。

**流转被拒，说要填某个字段。** 那是飞书的流转表单必填项，插件在写之前先查了一遍。按提示把值告诉书记员。

**hook 拦下了一条看起来无害的命令。** 多半是命令里藏着飞书命令行，hook 看不到里面在做什么。把它拆成单条简单命令重试；插件自己的脚本只在内容和清单一致时被信任，改过就会被拦。

**想先在不连飞书的情况下看看会发生什么。** 台账脚本默认只预览；加 `--offline` 连读都不读，只打印命令。

## 还没实测的部分

初稿里有几处机制只按文档写了，还没在真实会话里跑过。第一轮闭环前建议先做这几个最小实验，结果记下来，作为要不要调整机制的依据：

| 编号 | 要验证的 | 不成立时 |
| --- | --- | --- |
| V1 | 入口 → 序列 +2 → +1 → +0 三层派发能跑通，hook 认得每一层 | 调大嵌套层数，或由入口直接派 +1、+0 |
| V2 | `claude --agent alg-p2` 开的会话里，hook 收到的身份是 alg-p2 | 聚焦会话改用单独的工作目录 |
| V3 | 聚焦会话开着时，入口派不出同一个 +2 | 靠入口登记兜底 |
| V4 | 收件箱的消息在聚焦会话下一轮能看到 | 在聚焦会话里手动查收 |
| V5 | 用 SendMessage 能接着上次的 +2 干活 | 每次重派，靠状态包接续 |
| V9 | 只有书记员能写台账 | 加写入队列 |
| V10 | 路由不误判 | 补全状态包的简介；要求消息带工作项 ID |
| P1 | 桌面会话的 hook 环境里有桌面会话 ID，子会话一启动就能按预登记认领 | 子会话照开局 prompt 运行 `route.py claim`，hook 在这条命令结束时认领 |
| P2 | 开局 prompt 和别的会话发来的消息，收方的 hook 都能看到 | 收到的记录改由发方记；提醒改在收方第一次调用工具时附上 |
| P3 | 同一类权限模式下，不同家族的会话之间消息能送达，对方随即开始一轮 | 跨序列的派活改成收件箱留言，由你点开对方会话；还不行就回到 CLI 模式 |
| P4 | Auto 模式下，由别的会话来信开始的轮次里，派活、写台账、改文件不被拦 | 常用命令已写进精确的 allow；仍被拦的，换权限模式，或由你在场时做 |
| P5 | 开会话时模型写 opus、sonnet、haiku 这样的别名能生效 | 开好以后再改模型 |
| P6 | 二十多个会话同时开着，本机内存够用 | 调小 `pool.max_sessions`，用 `pool.later` 推迟不急的序列 |

台账脚本读飞书的部分，按真实空间上录下的输出改过并测试过：工作项、可流转状态和表单、文档大纲和区段、建文档的返回、条件查询（有结果、空结果和翻页）。查询每页最多 50 项，多出来的按返回的 session_id 翻页，后面哪一页读不懂也停下报错；超过 1000 项只读前 1000 项并提醒。私聊监听在写入测试里收过一条真私聊，按它的结构写进了收件箱；`meegle user me`、`project search`、`whoami`、知识空间列表、按标题读“状态包”那一节都没录过，脚本按文档写。读不懂时：工作项、项目、当前用户和台账查询会停下报错；知识空间查不到会提醒，按清单人工核对。

写的部分在 2026-11-01 的写入测试里跑过一轮：登记（建工作项、带角色人员、用标准输入建主文档）、流转（含带表单的）、替换状态包、追加交接记录、建节点、移动子树，以及飞书私聊监听。移动子树后原链接照样能打开，当前负责人为空的工作项也能流转。还没在空间里跑过的写法有：答复、立项单登记（建“项目”）、登记中途失败后的续做（`--resume`、`--doc`）、角色人员的补写、`tenant_domain` 的写回。第一次用时先预览，再在测试项上执行；正式发出的需求包不拿来测。测监听时用 `--max-events 1` 要注意：它数的是 lark-cli 收到的事件，别人私聊机器人的也算，第一条要是别人发的，监听什么都不记就退出。

2026-11-03 的补充验证：在 std_template 新增公开“阻塞”条件视图并加入空间置顶后，复制空间未带出该视图，系统预置“全部”视图正常带入。初始化现已移除视图查询、补建和验收要求。Codex 的当前验收规则见 [Codex 适配](Codex适配.md)。
