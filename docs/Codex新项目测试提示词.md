# Codex 新项目初始化测试提示词

在 Codex 中把新建的本地文件夹添加为项目，然后在该项目的新聊天中粘贴以下正文。这里测试的是 Codex 桌面应用当前项目中的可见聊天会话。

## 可直接粘贴的正文

请在当前新项目目录中，实际测试 agent-org 的 Codex 适配版，完成飞书项目、飞书文档知识库和 Codex 角色会话三处初始化，并验证它们能协同工作。

测试来源是 `https://github.com/Touricks/SuperOrgAgent` 的 `codex/desktop-adapter` 分支，预期插件版本为 `0.5.1-codex.1`。先记录实际取得的提交哈希，核对已安装插件的版本和内容。已有同源且内容一致的本地副本可以复用；否则把该分支克隆到当前项目的 `.plugin-src/agent-org`，不要覆盖已有目录。通过插件市场正常安装或更新，不手改安装缓存。读源码中的 `docs/Codex适配.md` 以及 Codex 的 setup、entry、ledger 技能后执行。

这是一次独立测试。我明确授权：在当前目录创建测试所需文件；从已有模板复制一个新的飞书项目测试空间；创建一个新的测试知识空间及其节点；创建默认 21 个 Codex 角色聊天；给它们命名，并置顶七个 +2 和 PMO +1；发送这些聊天之间完成本次初始化、派活、登记、交回和验收所需的消息；在本次新建的测试空间内创建和更新少量测试工作项与文档。已有模板、其他项目、聊天和置顶项保持原样。模型继承当前用户设置。

请直接完成已授权步骤。只有缺少账号权限、存在无法消除的目标歧义，或产品要求我亲自登录、审阅 hooks、重开聊天时，才说明具体需要我做什么。工具没有某项能力时，检查现有网页操作能力；仍无法完成的如实记录，继续完成不依赖它的部分。

按以下顺序执行：

1. **确认环境和测试范围。** 检查当前目录、Codex 项目和主机 ID、插件版本、飞书及 Meegle 登录身份、原生聊天工具和 hooks 能力。以本地文件夹名加本次测试时间生成唯一测试名称，将名称、来源提交和后续对象 ID 记录到 `test-report/`。遇到中断后沿用同一轮记录，避免重复创建。不要自动初始化当前目录的 Git 仓库。

2. **准备飞书项目与知识空间。** 从插件配置指定的模板空间读取结构，默认是 `std_template`；按实际查询到的 ID 核对，不凭同名猜测。用现有配置复制机制建立独立项目空间，CLI 不支持的复制操作可用网页完成。创建对应的独立测试知识空间，并回读真实 ID 和链接。此阶段先完成空间准备，再生成项目 hooks。CLI 能创建已有类型的工作项实例，不能把它当成新增工作项类型的能力；模板结构缺失时列出具体差异，保留模板原样。

3. **初始化本地项目并绑定。** 使用 `runtime: codex`、`mode: pool`，默认七个序列各一个 +2、+1、+0，共 21 个池位。任务描述写“验证插件初始化及跨端交接”，不开展真实研究实验。填写已核对的项目空间和知识空间，预览后执行初始化与飞书绑定。保留已有用户文件，核对实际类型、字段和流程模板 ID。

4. **启用 hooks 并开出角色聊天。** 如 Codex 要求我在 Settings → Hooks 审阅并信任，给出具体操作，然后等待我完成；不要改信任记录或绕过检查。使用原生工具、创建预约和真实 threadId/hostId 开池，等待开局完成并核对角色绑定。排队返回的 clientThreadId 不当成真实 threadId。临时子智能体不代替长期角色聊天。置顶顺序为 PMO +2、PMO +1、产品 +2、算法 +2、工程 +2、基础设施 +2、质量 +2、外联 +2；回读原生置顶列表验证，不只记录调用成功。

5. **由书记员建立正式文档骨架。** 确认唯一书记员已经绑定且真实 hook 已运行，再由该会话预览并执行 `ledger.py ensure-node all`，建立插件规则要求的知识库目录。按照插件流程登记测试项目的立项记录，回读项目级工作项和主文档。先有空间、角色与写入身份，再建正式节点，避免开局互相等待。

6. **完成一次真实交接。** 由 PMO 入口安排一个只涉及测试文件的小任务，按角色分工起草需求包，由书记员登记已知类型的工作项和主文档。给执行角色发送带工作项 ID、包路径和消息 ID 的指令，核对收到回执。执行角色产出交付包，质量角色独立核对并产出验收结果，由书记员登记回复和允许的状态变化。把工作项、文档、负责池位和实际聊天 ID 对上。正式文档、字段和状态由书记员写入；交付包和验收包回复原工作项，不重复建同类任务。

7. **检查恢复与重复执行。** 重跑初始化和开池计划，确认沿用原空间、节点和聊天。重复提交同一条消息登记，确认复用原消息记录。用 `context` 从台账、状态包和回执恢复上下文；验证消息已排队、已收到、已处理和工作项已验收分别有证据。发送或创建结果未知时先核对原对象，不盲目重试。此次无需额外创建替换聊天。

8. **交付测试结果。** 运行插件 check，在 `test-report/` 保存报告和必要的原始回执，凭据与完整认证输出不要写入报告。分别报告飞书项目、飞书知识库、Codex 会话以及跨端交接的“通过／失败／阻塞／未执行”，附对应链接、ID 和验证依据。真实空间或会话尚未建立时，不能用本地文件、模拟数据、工具返回成功或旧测试结果代替完成证据。将插件缺陷与账号权限、工具缺失分开记录，给出复现步骤；不要修改插件规则或手改状态来消除失败。

完成后告诉我三个地方是否都初始化成功、交接是否跑通、是否具备进入主版本合并评审的条件，以及仍需修复的问题。保留测试对象供我检查，本次不自动清理，也不合并或推送主分支。
