# Codex 新项目初始化测试提示词

在 Codex 中将一个新本地文件夹添加为项目，在新聊天中粘贴正文。预期版本为 **0.5.1-codex.4**；先核对取得的源码与已安装版本。此提示词分别验证五分钟配置和完整业务交接。

## 可直接粘贴的正文

请在当前新项目实际测试 agent-org Codex 版，完成飞书项目、飞书知识库和 Codex 角色会话三处初始化。下载插件后的首次配置目标为 300 秒，后续完整派活和验收另行计时。

测试来源为 SuperOrgAgent 的 main 分支，预期插件版本 0.5.1-codex.4。仓库地址：https://github.com/Touricks/SuperOrgAgent 。优先复用版本一致的本地来源，否则克隆到当前项目的 `.plugin-src/agent-org`，不覆盖已有目录。记录实际提交和工作区差异，通过正常插件流程安装或更新，不手改缓存。实际版本不符时先停止并报告来源差异，不将旧版测试记成新版结果。

我明确授权：创建当前项目所需文件；从已维护的模板复制独立飞书项目空间；创建独立知识空间及节点；创建默认 21 个 Codex 角色聊天并命名；发送本项目角色之间初始化、派活、登记、交回和验收所需的消息；在新建测试空间中创建和更新少量测试工作项及文档。全部角色保留在本项目，不做全局置顶。已有模板、其他项目和聊天保持原样，模型继承当前设置。

角色标题直接使用计划中的 `[项目名] <池位名>`，例如 `[项目名] RnD-p0-01`；不追加中文序列名、重复职级或“池位”等后缀。

禁止在初始化中使用 computer-use 配置飞书视图。不要创建、补建或检查六个自定义视图，不把缺视图列为失败。只能复制已经维护好的空间结构；模板缺类型、字段或流程时报告阻塞，不能在测试中修改模板或现场搭建这些结构。复制空间本身可在上述授权范围内通过网页操作。

请直接完成已授权工作。确实需要本人登录、信任 hook 或解决权限问题时说明具体动作；等待时间计入首次配置。发生阻塞后保留对象和起点，继续独立部分，不伪造通过，也不重置计时。

### 配置阶段：目标 300 秒

1. **开始计时并做一次环境检查。** 下载到插件后、开始安装配置前，运行插件 `scripts/codex_onboarding.py begin --target <当前目录>`。随后检查 Codex/CLI 版本、两边认证、原生会话工具、当前项目和主机 ID。使用文件夹名与本次时间生成唯一测试名称，将来源和 ID 保存到 `test-report/`。认证、安装依赖、复制、人工等待及最后检查全部计入。不要自动初始化 Git 仓库。
2. **准备两个空间。** 只读核对 std_template 或任务指定的真实模板；复制独立项目空间，创建独立知识空间并回读 ID 和链接。按 project_key 指定目标，避免同名歧义。只创建已有类型的实例，不新增类型。新用户不能访问模板或缺少必要权限时，记录首次配置阻塞。
3. **生成并绑定。** 使用 runtime=codex、mode=pool、七序列共 21 个池位，任务为“验证插件初始化及跨端交接”。依 setup 技能预览并执行本地初始化与飞书绑定，保留用户文件。不要重复运行完整模板检查、完整回归或研究访谈。
4. **启用 hooks 并创建聊天。** 在产品要求时等我审阅并信任项目 hooks，不改信任记录。优先开默认书记员，再每批至多 4 个独立创建其余聊天；每个池位执行 reserve → create_thread → bind。等待实际开局，clientThreadId 不当作 threadId，未知结果先核对，临时子智能体不代替角色聊天。回读全部 projectId 交给 observe，核对 21 个角色都留在本项目；七个 +2 和 PMO +1 的查找顺序见 `org/会话入口.md`，不要声称固定了项目内部排序。
5. **正式知识节点及最小立项。** 默认书记员或明确承接配置任务的主会话执行 ensure-node all，回读 29 个节点的 ID、标题和父子结构；其余聊天可同时完成开局。登记一份最小测试立项单，回读项目级工作项和主文档，不开展实际研究。
6. **结束配置计时。** 完成当次三处回读后运行 setup check 和 codex_onboarding finish。核对每个角色的 PreToolUse，整体 SessionStart/Stop，不要求 UserPromptSubmit。记录起止时间、总耗时、人工等待、各系统读回和完整立项回执。timing_pass 不是远端验收证据，超过 300 秒如实失败，不先准备好再计时。

### 业务阶段：独立计时

7. **需求与开工顺序。** 起草只修改一个测试业务文件的小需求，同时明确允许的草稿、交付、送审和独立证据目录。书记员登记需求、主文档和负责池位，先流转到执行中并回读，再通过 message 派活。接收者先 ack，再运行 start，核对通过后才创建业务文件或过程材料。留存状态回读时间和首次产物时间，不能先写产物再补状态。
8. **交付与独立质量。** 执行角色产出交付包，书记员登记并将来源项改为待验收，送审项为待核查，再给质量角色发送 review。质量角色显式 ack、start，独立检查并产出验收包，书记员登记结果。交付和验收回复原工作项，不另建同类任务。核对正式文档标题没有多余的前导 `#`。
9. **恢复与保护检查。** 重跑计划与初始化，确认空间、节点、工作项和聊天 ID 沿用。重复消息登记返回 reuse；queued、received、handled、已验收分别有依据。使用合法草稿/evidence 的原生 apply_patch 检查误拦截已消失；配置、评测及符号链接保护仍生效。发送结果未知先查原消息，不换 ID 盲目重试。本轮不另建替换聊天。
10. **报告。** 在 test-report/ 中分别记录：三处配置、300 秒首次配置、业务交接、恢复与保护的通过／失败／阻塞／未执行，附当次原始回执、链接、ID 和复现步骤。凭据和认证原文不入报告；本地夹具、旧测试或工具成功返回不能代替远端回读。不要手改池状态或插件规则来消除失败。

最终告诉我首次配置是否在五分钟内完成、三处是否可用、业务交接是否通过，以及是否具备主分支合并评审条件。保留测试对象，本次不自动清理，不推送或合并主分支。
